# Development account infrastructure

This module owns the account API, deletion worker, authenticated gateway, service identities, restricted Identity Platform API key, secret, build repository/bucket, hourly scheduler and cleanup alert policies. It does not implement or deploy the session/grading services in #18. Google OAuth registration, installed native builds and #61 remain independent completion gates.

The accounts identity can verify/disable users and read/write account metadata; only the deletion identity can erase users and score records. Gateway invocation is bound at the private service, scheduler invocation at the worker job, secret access at the one secret, and build artifact access at the build repository/bucket. No identity receives Owner, Editor or a downloaded key. Cloud Run scales from zero to at most two instances. The scheduler runs hourly in UTC. Logs contain operational counts; public request bodies and credentials must never be logged.

## Bootstrap and deployment

Requires Terraform 1.9+, gcloud, Firebase CLI and Python 3.12. Commands below run from the repository root in PowerShell. Use the project ID explicitly. Do not change unrelated gcloud defaults.

1. Create the state bucket once with `gcloud storage buckets create gs://casestudy-tech-dev-2e03d0-tfstate --project=casestudy-tech-dev-2e03d0 --location=us-central1 --uniform-bucket-level-access --public-access-prevention` and enable versioning with `gcloud storage buckets update gs://casestudy-tech-dev-2e03d0-tfstate --versioning`. The state contains the API key as provider-managed sensitive data. The private state bucket is separate from build staging; never grant build/runtime identities state access, download state into source, or print it. Local plans and Terraform internals are ignored.
2. Set a short-lived token for the current shell: `$env:GOOGLE_OAUTH_ACCESS_TOKEN = (gcloud.cmd auth print-access-token --project=casestudy-tech-dev-2e03d0 --quiet) -join ''`. Do not echo it. Initialize with `terraform -chdir=infra/accounts init -backend-config=bucket=casestudy-tech-dev-2e03d0-tfstate -backend-config=prefix=accounts/development`.
3. On a new environment, create only the bootstrap graph first: required APIs, service identities/custom roles, runtime IAM, artifact repository/build bucket/build IAM, restricted key, secret and secret IAM. Use explicit `-target` arguments for these resources. This exceptional two-stage bootstrap lets the image and secret exist before Cloud Run starts. Inspect the saved plan before applying. Subsequent deployments use the full plan, and finish with a full no-change plan.
4. Run `python infra/accounts/bootstrap_identity_secret.py`. The restricted key is transferred in memory from API Keys to Secret Manager; no value is printed or placed in env files. This creates a new secret version, so run it only for initialization/intentional rotation. The hardcoded development project prevents accidental cross-project copying; parameterize/review before using another environment.
5. Build tested source with `gcloud builds submit services/accounts --config=services/accounts/cloudbuild.yaml --substitutions=_IMAGE=us-central1-docker.pkg.dev/casestudy-tech-dev-2e03d0/accounts/accounts:YOUR_REVISION --project=casestudy-tech-dev-2e03d0 --region=us-central1 --service-account=projects/casestudy-tech-dev-2e03d0/serviceAccounts/cst-build@casestudy-tech-dev-2e03d0.iam.gserviceaccount.com --gcs-source-staging-dir=gs://casestudy-tech-dev-2e03d0-account-builds/source`. Logging uses Cloud Logging, avoiding mutable log-object access. Check the build succeeded; an uploaded image from a failed build is insufficient.
6. Plan/apply the full module with `-var=image=us-central1-docker.pkg.dev/casestudy-tech-dev-2e03d0/accounts/accounts@sha256:VERIFIED_DIGEST`. Deploy the tested Firestore rules with `firebase deploy --only firestore:rules --project casestudy-tech-dev-2e03d0`. This does not deploy the unfinished student bundle.

On first creation, Cloud Monitoring can take up to ten minutes to recognize newly created log metrics. If an alert-policy operation returns `Cannot find metric(s)`, wait for descriptor propagation while inspecting the rest of the deployment, then rerun a full plan/apply. Do not delete metrics, disable alerts or report a partial first apply as successful. Verify the final plan has no changes.

Do not enroll real students until Google OAuth, native verification, notification destinations, public-auth abuse controls and #61 are resolved. Alert policies create Cloud Monitoring incidents; attach verified notification channels for on-call delivery before student use. The fixed origins allow only this project's Firebase hosting domains. Review explicitly before adding development/custom origins.

## Live verification

- `terraform validate`, `terraform fmt -check`, backend/client checks and demo-emulator rules/store checks must pass before deployment. Explicit gateway OPTIONS operations bypass student JWT checks only for CORS preflight; protected GET/POST operations retain JWT verification and independent backend verification.
- Verify gateway `/health` returns 200, protected routes with absent/forged tokens return 401, and direct unauthenticated Cloud Run access returns 403. Verify allowed-origin preflight succeeds and another origin receives no CORS permission. Never paste real tokens into commands or logs.
- Run `python infra/accounts/check_gateway.py` from the repository root for the six credential-free gateway checks. For rendered route regression checks, export web from `apps/student` with `npx expo export --platform web --output-dir dist`, install the isolated browser with `uvx --from playwright==1.64.1 playwright install chromium`, then run `uv run --no-project --python 3.12 --with playwright==1.64.1 --with pytest==9.1.1 python -m pytest infra/accounts/test_web_routes.py -q` from the repository root. These seven anonymous browser checks do not exercise Google OAuth. See [the integration evidence](../../docs/implementation/issue-4-live-verification.md) for cloud and installed Android results.
- Inspect runtime and invoker IAM; gateway has no database/secret role and scheduler has no account-data role. Confirm service account project roles are the custom roles in this module, not broad inherited Editor roles.
- The opt-in synthetic worker probe uses the current gcloud principal and generates two anonymous fixture identities (no emails or session content). Run `uv run --project services/accounts --python 3.12 python infra/accounts/live_deletion_probe.py seed --fixture tmp/verification/live-deletion.json`, trigger the actual Cloud Scheduler job, wait for a successful Cloud Run execution, then run the same command with `verify`. Verification checks actual account/score removal before the original deadline, retained denial state, and preservation of the second owner's records; it then cleans up the fixtures. A failed probe leaves its ignored fixture file for recovery. This does not substitute for signing in with Google and exercising deletion through the student UI.

## Recovery

Keep failed deletion requests queued with their original deadline; inspect count-only worker logs and retry executions rather than deleting metadata. Account and worker resources have deletion protection. Use a previously verified image digest for rollback, plan/apply it, then rerun health/access checks. Do not make Cloud Run public to solve a gateway invocation problem. Preserve completed denial markers until all old ID tokens have expired.
